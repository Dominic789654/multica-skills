# 可移植 SoulDraw 技能套件

> 目标：将用户的原始请求转化为稳定的图表简报，再转化为有效的 draw.io / mxGraph 更新。

此套件由四个协同模块组成：

- 规划 / 简报规范化：在执行前澄清真实的图表任务。
- 提示词扩展 / 候选方案塑形：当用户需要示例、变体或结构化头脑风暴时生成备选方案。
- 图表执行与反馈迭代：在简报稳定后创建或修订 draw.io / mxGraph 内容，并基于用户不满意反馈进行增量修订。
- 渲染回看 / 视觉自检：将持久化后的图表渲染成 PNG 或等价截图，审查文字与图形位置关系、箭头连线、重叠遮挡，以及紧凑但不影响阅读的布局，并按审查准则（rubric）修补迭代。

默认交付优先级固定如下：先把可编辑 XML 写入宿主定义的源工件，再尽可能向用户展示 PNG / 截图等可视预览；只有当用户明确索要源 XML，或宿主既不能持久化工件也不能展示预览时，才把 XML 本体直接放进聊天最终回答。

### draw.io XML 生成对齐

此套件遵循 draw.io 的 AI 生成指南：

- 图表可以表示为完整的 `.drawio` 文档（`<mxfile><diagram><mxGraphModel>...`），也可以表示为裸 `<mxGraphModel>`。
- 对单页 AI 生成，优先使用裸 `<mxGraphModel>`，因为它更容易生成、检查、校验和修补。
- 持久化纯文本、未压缩 XML。不要把压缩/base64 图表载荷生成为源工件；压缩只保留给宿主特定的导出或 URL 创建流程。
- 导出使用 PNG（由 draw.io 导出），不生成 SVG。
- 当宿主提供校验器或重试反馈时，在保存或交付前校验生成的 XML。

### 交付优先级与 XML 回退纪律

大多数“帮我画一个 draw.io 图”的请求，本质上要的是图，不是整段 draw.io 源文本。默认先交付可视预览，再把 XML 留在宿主工件里。

只有在以下任一条件成立时，才进入“直接输出 XML 到最终回答”的回退模式：

- 用户明确要求“把可编辑 XML / mxGraphModel 文本直接给我”。
- 当前宿主明确要求最终回答本身承载 XML，而不是写入工件后展示图像。
- 当前环境无法写入工件，也无法展示 PNG / 截图 / 编辑器链接，只剩纯文本回退路径。

一旦进入 XML 回退模式，请遵守以下规则：

- 最终回答只输出 XML 本身，不添加说明、前言、结尾、Markdown 代码块或 ```xml fence。
- 单页图表的第一个非空白字符必须是 `<mxGraphModel`，最后一个非空白片段必须是 `</mxGraphModel>`。
- 不要输出 `<?xml ...?>` 声明，除非宿主明确要求完整文件头；benchmark、粘贴保存和大多数单页 draw.io 生成场景都优先裸 `<mxGraphModel>`。
- 如果用户要求 Mermaid、Markdown、压缩/base64 或其他格式，但任务目标仍是 draw.io 图，遵守 draw.io 契约，输出裸 `<mxGraphModel>`。
- 如果只是解释流程或规划候选方案，不输出 XML，也不声称已经修改图表。
- 对含有枚举项的请求，生成 XML 前先在内部建立实体清单和关系清单；最终 XML 只能包含清单里的节点和关系。不要因为总数、标题、候选契约或自己的常识暗示更多元素，就补充未列出的部门、角色、阶段或叶节点。
- 生成 XML 后必须做一次内部结构与几何自检：结构单元存在、ID 唯一、边端点存在、每个可见单元有几何、同一父级下的可见节点没有重叠、所有节点都落在 `pageWidth` / `pageHeight` 范围内。纯 XML 交付时不把自检文字写进最终回答，而是用通过自检的 XML 体现结果。
- 纯 XML 交付默认输出干净的裸 `<mxGraphModel>`；不要为了展示内部自检而新增 XML 注释、说明节点或其他非业务内容。
- 严格增量编辑例外：如果用户要求“只增加/只替换/不要修改其他任何内容”或输入工件本身没有注释，就继续保持最小 XML diff；不要为了“解释已校验”额外引入任何节点、注释或属性。
- 不要把验证、布局意图或“主路径从左到右”等内部说明做成可见文本节点或 XML 注释。可见文本只用于用户真正需要的标题、图例、业务注释或真实图表内容。

### 高频边界条件

遇到以下情况，优先按“先收敛边界、再生成图表”的顺序处理。不要为了尽快产出，把歧义直接固化进 XML：

- **范围爆炸**：当用户要求“全景图”“所有内容”“越全越好”“层次越深越好”时，先把范围边界、受众和节点密度上限收紧；如果两轮内仍不清楚，默认收敛成一个可读的中等密度版本，而不是生成失控大图。
- **格式歧义**：当用户同时提到 draw.io、Mermaid、PPT、海报或"给我一个可编辑版本"时，先判断本轮交付物究竟是规划文本、宿主内可编辑源、还是给用户直接看的导出副本。用户若只是要"画出来"，默认目标是图像预览（PNG），不是把裸 `<mxGraphModel>` 倒进聊天窗口；不要把多种格式混在同一次最终回答里。
- **严格增量编辑**：当用户要求“只改一处”“不要动别的”“保留现有风格/ID/坐标”时，视觉优化只能发生在受影响闭包内；不要借机整体重排、重配色或新增大容器。
- **长标签 / 中英混排 / 多行文本**：优先扩节点宽度、增高度、分层文本或拆成主标签 + 辅助说明，不要靠把字号压到难读、把节点压窄或允许文字溢出来换取紧凑。
- **箭头 / 线条可读性**：当布局紧凑度、样式美观和箭头可读性冲突时，优先保证箭头头部、端点和主路径方向一眼可辨；不要让主链箭头消失在节点边界里，也不要用穿过节点正文的连线换取省空间。
- **边标签 / 文本归属**：边标签、旁注和节点正文必须各自占据稳定位置；不要让线条压过正文、让标签直接贴在线上，或让说明文字悬在多个图形之间使读者猜测归属。
- **跨容器 / 跨泳道关系**：如果真实父子结构会让跨区连线难以稳定表达，优先把分区做成根层轻量背景，把连接节点留在根层；只有确实需要包含关系时才让节点进入容器内部。
- **容器稳定性**：一旦选择手工坐标控制容器、泳道或分组内的节点位置，就不要再叠加会自动重排子节点的布局属性；子节点必须在渲染后稳定留在所属容器内。
- **视觉目标与语义目标冲突**：当“更漂亮”和“更准确/更稳定/更可增量编辑”冲突时，优先级固定为语义正确性 > 契约稳定性 > 可读性 > 视觉装饰。
- **无真实预览环境**：可以完成结构校验和布局自检，但不得声称已经做过真实渲染级视觉验收；这时应明确剩余风险集中在箭头、标签位置和实际观感上。
- **高保真复刻请求**：用户要求参考论文图、示意图或截图时，优先复刻结构关系、阅读顺序和关键视觉对比；如果原图依赖并排 panel、子图 caption、统计 callout、矩阵高亮、participant/lifeline 或消息箭头顺序来表达含义，这些都属于阅读契约，应一并保留。若原图存在不利于 draw.io 维护的技巧，保留其视觉意图而不是机械复制。
- **节点数量过多**：单张图开始出现“所有节点都重要”的迹象时，优先引入分区、两行证据链、簇布局或拆成主图 + 子图规划；不要把几十个节点硬塞成一排或一棵过宽的树。

多个边界同时出现时，先决定输出边界和修改边界，再决定布局和风格；不要反过来先选视觉方向。

## 1. 规划模块

### 职责

- 当简报含糊，或用户要求示例、拆解、多个候选方向时，先在文本规划层工作。
- 保留用户的核心目标、领域和硬性约束。
- 在执行前规范化原始简报，让后续图表工作拥有更干净、更稳定的交接。
- 保持规划与执行紧密相连：规划是为了改善 drawio 结果，而不是变成脱离实际的写作练习。

### 规划原则

- 默认生成 8 到 10 个变体，除非用户明确要求其他数量。这个数量既足以覆盖真实的可能性空间，也不会让选择本身变成负担。
- 变体必须有实质差异。如果两个方案可以互换，就合并其中一个；浅层同义词替换对用户没有价值。
- 尽可能保持用户原本使用的语言，避免无意义的语言切换带来认知摩擦。
- 如果用户只要求拆解或示例，不要触碰宿主图表源文件，也不要声称图表已经更新。规划层和执行层的边界必须清楚。
- 默认直接推进并做出合理假设。不要把样式、配色、紧凑度、标题措辞等可后改问题升级为前置追问。
- 只有缺失细节会实质改变输出格式、节点集合、关系拓扑、严格增量编辑边界或范围上限时，才进入短澄清；澄清的目标是收紧边界，不是把方案设计责任转交给用户。

### 规范化清单

将原始简报规范化为：

- 目标结果
- 预期受众
- 必须保留的元素
- 可选偏好
- 禁止或不想要的特征

## 2. 提示词扩展与候选方案塑形

### 澄清触发门（前置判断）

在展开候选方案或直接执行前，先判断是否命中必须收边界的硬条件：

**未命中硬条件，直接推进**：若用户已经给出可落图的目标和基本内容，就直接进入工作流步骤 1，并在必要时自行补足低风险假设。以下问题默认不要先追问：
- 样式偏好、配色方向、紧凑度取舍、标题措辞、装饰性图例
- 可以在首版图出来后再微调的布局细节

**命中硬条件，启动短澄清**：只有当缺失信息会实质改变图表骨架时，才进入互动环节。硬条件包括：
- **输出物不明确**：draw.io、mxGraph、Mermaid、海报、截图预览或可编辑 XML 之间存在冲突
- **结构不明确**：节点集合、父子关系、主路径方向、分区方式或关键连接关系存在两种以上合理解释
- **修改边界高风险**：用户要求“只改一处”“不要动别的”，但该修改可能牵连布局、坐标、ID 或相邻连线
- **范围可能失控**：出现“全景图”“越全越好”“所有内容都放进去”等信号，不先收边界就大概率生成失控大图

进入短澄清后，遵守以下纪律：
- **最多进行 1 轮追问**，只问 1 到 2 个最关键的问题，不要一次列出长问卷。
- 追问时先给出默认理解或候选假设，让用户确认或修正，而不是把决策责任全部推给用户。
- 如有必要，可进行网络搜索（如搜索行业流程标准、缩略词含义、领域知识背景）来补充上下文，减少追问。
- **1 轮结束后无论信息是否完全齐备，都进入执行**，基于现有信息做合理假设并生成图表，在交付时注明关键假设。

### 工作流

1. 使用上面的清单规范化简报。
2. 选择 3 到 5 个变化轴（结构类型、布局方向、信息密度、语气、强调重点等）。
3. 生成 8 到 10 个变体，保持同一个核心任务，只改变选定的轴。
4. 使用易于比较的 Markdown 小节格式化响应，每个候选方案独立成节。
5. 如果用户想从某个选项继续，用紧凑形式重述所选方向，并进入宿主的图表执行流程。

### 多样性规则

- 每个变体应有一个主要差异点，最多两个次要差异点。
- 让变体分布在结构、密度、语气和强调重点上，而不是只改变形容词。
- 避免近似重复。如果两个变体感觉可以互换，合并或替换其中一个。
- 保持方案集平衡：同时包含更稳妥和更大胆的选项。

### 输出策略

- 优先使用易于比较的 Markdown 小节。
- 让每个候选方案都能独立复用为提示词或计划种子。
- 当一两个变体最适合已陈述目标时，包含简短推荐。
- 以紧凑的下一步菜单收尾：选择一个候选方案、合并两个候选方案，或继续进入执行。
- 规划学术海报、展板或 A0/A1 版面时，每个候选方案必须给出列数、行高比例、视觉重心、图示/图表占位区分配、适用评审偏好，并包含具体可读性建议：A0 竖版约 84 × 119 cm，建议外边距约 2.5 到 3.5 cm、栏间距约 1.5 到 2.5 cm，并把栏宽/占位区换算成物理空间约束；标题/作者/正文/脚注应形成明确字号层级，正文区避免低于远距离阅读可接受的字号，图表区优先保留 35% 到 50% 的版面权重，对比度和留白按会议现场 1 到 2 米观看距离校准。
- 海报规划的对比度建议要成体系：浅底深字，正文文字与背景满足高对比；同级区块使用一致标题色和线宽，图表线条/坐标轴/图例在打印后仍清楚；不要只说“高对比”，要说明色彩层级、边框线宽、图表线宽或无障碍可读性取舍。

## 3. 交接边界

- 如果用户只想要示例，保持在规划模式。
- 不要把并未发生的执行描述成已经完成。
- 如果用户选择了候选方案，用紧凑形式重述所选方向，并保留用户在选择后添加的额外修改。
- 如果用户要求合并候选方案，先在简报层合并，再执行。
- 规划模块负责拆解、候选方案塑形和交接措辞。
- 执行模块负责对宿主定义的图表源工件进行真实图表编辑。

## 4. 公开宿主契约

这一版公开契约保持宿主中立。

- 宿主需要为当前任务定义一个可持久化的 draw.io 图表源文件，或等价工件。
- 宿主需要为该工件范围提供读取、写入或替换、定向编辑，以及列出/发现能力。
- 宿主应在可用时暴露校验和重试反馈。
- 宿主应说明作用域内工件是裸 `<mxGraphModel>` 还是完整 `.drawio` 包装。如果二者都接受，此技能应为单页图表写入裸 `<mxGraphModel>`。
- 除非宿主契约明确提供，否则不要假设固定文件名、工作区路径、品牌名或具体工具签名。
- 最低要求行为见 `references/host-contract.md`。

## 5. 公开图表执行模型

### 执行原则

这些规则背后有同一个原因：draw.io 图表一旦出现 ID 冲突、悬空边或压缩源文件，往往无法被正常渲染，而且问题通常要到用户打开文件时才暴露。保持以下习惯，可以让每次交付都更容易被 draw.io 直接加载：

- 将宿主定义的图表源工件视为当前图表的单一事实来源。
- 如果工件缺失，先从基础模板创建它，再编辑。
- 当用户要求修改现有图表时，默认进行增量编辑：先读取当前工件，识别受影响的单元，并保留未受影响的内容、ID、标签、样式、几何和连接关系。
- 除非用户明确要求完整重做、重绘、重置、重建或新图表，否则不要替换或重绘整个工件。
- 保持源工件为纯文本且未压缩。绝不要把生成的 base64/deflate 内容持久化为可编辑源。
- 当最终回答本身是可保存的 draw.io XML 时，直接输出裸 XML 文本；不要用 Markdown 代码块、反引号围栏、说明段落或“下面是 XML”之类的包装。本文档中的 XML 围栏示例（fenced XML）仅用于展示，不是交付格式。
- 导出预览使用 PNG（由 draw.io 导出），将可编辑工件保持为纯 draw.io XML。
- 保持 XML 有效：对常规单页形式，应有一个 `<mxGraphModel>`、一个 `<root>`、一个 `mxCell id="0"` 和一个 `mxCell id="1" parent="0"`。如果宿主要求完整 `.drawio` 包装，除非宿主明确要求多页，否则只围绕同一模型保留一个选中的 `<diagram>`。
- 保持每个 `id` 唯一。绝不要让 `source` 或 `target` 指向缺失节点。
- 顶点和边互斥：形状使用 `vertex="1"`，连接线使用 `edge="1"`。
- 不要把一个 `<mxCell>` 嵌套在另一个 `<mxCell>` 内。如果需要元数据，使用一个根级包装元素，并且其中只包含一个 `mxCell`。
- 每个可见节点或边都必须保留一个直接子节点 `<mxGeometry ... as="geometry"/>`。边的几何必须使用 `relative="1"`，并且不得在 `mxCell` 层级自闭合。
- 使用以分号分隔、形如 `key=value;` 的 draw.io 样式字符串。在普通单元样式中包含 `html=1`，让纯文本和已转义富标签一致渲染。
- 对标签值进行 XML 转义：`&`、`<`、`>` 和 `"` 不得在属性中原样出现。换行使用 `&#xa;` 或已转义的 `<br>`，不要使用字面量 `\n`。
- 匹配形状和周界（perimeter）。对椭圆、菱形、数据库、云图标或领域特定符号等非矩形形状，使用匹配的 draw.io shape/perimeter 样式，而不是通用圆角矩形。
- 默认先用 draw.io 的正交边，但不要把自动路由当作硬约束。只要出现长反馈边、跨分区或跨泳道连接、宽标签节点、并行分支拥挤，或箭头头部容易埋进节点边界的情况，就应主动为边预留走线走廊，并在 `mxGeometry` 中写 1 到 2 个中继点；只有在确实需要稳定进出边侧时才补 `exitX`/`entryX`，不要等视觉审查失败后再被动补锅。
- 容器内的子元素使用相对于容器的坐标，而不是页面坐标。使用真实父子包含关系，而不是仅把形状放在大型背景框上方；但普通学术分区、阶段背景或证据链背景如果会有跨分区连接，优先把分区做成 `pointerEvents=0` 的根层背景，连接节点仍放在根层并使用页面坐标，避免边跨父级带来的可移植性风险。只有泳道、组织包络、明确包含关系或宿主要求父子结构时，才把连接节点设为容器子节点。
- 除非用户要求更改，否则保留现有节点、边、标签和布局。
- 当用户要求新图表且没有明确样式指导时，默认采用精致的信息设计 / 适合幻灯片的视觉效果。

### 用户反馈驱动的增量修订（不满意时）

当用户明确表示“不满意”、提出新问题或追加新约束时，默认进入反馈驱动的增量修订流程，而不是直接整图重做：

1. 先把用户新反馈归类为以下之一：
  - 语义修订：内容缺失、关系错误、方向错误。
  - 表达修订：标签命名、文案语气、语言切换。
  - 视觉修订：配色、密度、间距、对齐、可读性。
  - 结构修订：新增分支、合并分支、局部重排。
2. 明确“保留区”和“修改区”：
  - 保留区：用户未否定且运行正常的节点、边、ID、布局与样式。
  - 修改区：被新反馈直接点名或被其影响到的最小闭包单元。
3. 对新增问题先做差量简报（delta brief）：只记录新增目标、硬约束和禁改项；不要重写整份简报。
4. 应用最小可行 XML 变更：优先补充、替换、重连或局部移动；仅当新增要求与现有结构根本冲突时，才进行局部重构。
5. 每轮修订后执行同样的结构校验与渲染回看；若仍不满足，再进入下一轮，默认最多 3 轮。
6. 若用户要求“换一个方向”但未要求重做，先给 2 到 3 个局部改造选项（例如保守版/平衡版/激进版），由用户选择后再落地增量修改。

不可妥协边界：除非用户明确要求“重做/重建/从零开始”，否则不要抛弃当前工件中已确认可用的部分；反馈迭代应以可追踪、可回滚的最小差量为优先。

### 基础模板

如果宿主定义的图表源工件不存在，先创建这个最小模板：

```xml
<?xml version="1.0" encoding="UTF-8"?>
<mxGraphModel dx="1000" dy="1000" grid="1" gridSize="10" guides="1"
  tooltips="1" connect="1" arrows="1" fold="1" page="1" pageScale="1"
  pageWidth="827" pageHeight="1169" math="0" shadow="0" background="#FFFFFF">
  <root>
    <mxCell id="0"/>
    <mxCell id="1" parent="0"/>
  </root>
</mxGraphModel>
```

页面级默认 `shadow="0"`、`background="#FFFFFF"`，与 `references/style.md` 的克制气质一致；轻阴影只在需要卡片感或汇报式层级时启用。对分解图、参与者卡片或同一语义层的主节点可以统一加轻阴影，但 lifeline、边和大多数注释文本仍保持无阴影。

### XML 模式

普通流程节点使用这个形状（浅底色 + 中性灰蓝描边，无阴影）：

```xml
<mxCell id="node-1" value="开始" style="rounded=1;whiteSpace=wrap;html=1;strokeWidth=1.5;fontSize=14;fillColor=#EFF6FF;strokeColor=#94A3B8;fontColor=#0F172A;spacing=10;spacingTop=8;spacingBottom=8;arcSize=12;"
  vertex="1" parent="1">
  <mxGeometry x="80" y="80" width="140" height="52" as="geometry"/>
</mxCell>
```

主路径锚点 / 关键结论节点应承担一级强调，使用更深底色 + 加粗字体（`fontStyle=1`）+ 略粗描边来区分主链与辅助内容。同图中通常只让 1 到 2 个节点达到这一级别，避免“每个模块都抢焦点”：

```xml
<mxCell id="node-anchor" value="核心结论" style="rounded=1;whiteSpace=wrap;html=1;strokeWidth=2;fontSize=15;fontStyle=1;fillColor=#DBEAFE;strokeColor=#2563EB;fontColor=#0F172A;spacing=10;spacingTop=8;spacingBottom=8;arcSize=12;"
  vertex="1" parent="1">
  <mxGeometry x="540" y="80" width="160" height="58" as="geometry"/>
</mxCell>
```

当图表包含分支时，使用语义化决策形状，而不是流程矩形。中性决策保持克制配色（不要默认使用警示色）：

```xml
<mxCell id="node-2" value="已批准？" style="rhombus;whiteSpace=wrap;html=1;strokeWidth=1.5;fontSize=14;fillColor=#F1F5F9;strokeColor=#64748B;fontColor=#0F172A;spacing=10;"
  vertex="1" parent="1">
  <mxGeometry x="280" y="70" width="128" height="76" as="geometry"/>
</mxCell>
```

只有当决策本身代表风险、限制、拒绝或异常分支时，才切换到暖色（如 `fillColor=#FEF3C7;strokeColor=#B45309;fontColor=#78350F`）；不要把每个 yes/no 节点都画成警示色。

当节点表示持久化数据时，使用数据库/圆柱形状：

```xml
<mxCell id="node-3" value="数据存储" style="shape=cylinder;whiteSpace=wrap;html=1;boundedLbl=1;backgroundOutline=1;size=15;strokeWidth=1.5;fontSize=14;fillColor=#ECFEFF;strokeColor=#0E7490;fontColor=#0F172A;"
  vertex="1" parent="1">
  <mxGeometry x="480" y="80" width="120" height="70" as="geometry"/>
</mxCell>
```

两个节点之间的主路径箭头使用这个形状：

```xml
<mxCell id="edge-1" value="" style="edgeStyle=orthogonalEdgeStyle;rounded=1;orthogonalLoop=1;jettySize=auto;html=1;strokeWidth=2;fontSize=13;strokeColor=#475569;fontColor=#334155;endArrow=blockThin;endFill=1;"
  edge="1" parent="1" source="node-1" target="node-2">
  <mxGeometry relative="1" as="geometry"/>
</mxCell>
```

反馈边、旁支边或证据边使用更轻的描边和虚线，与主路径形成视觉区分（避免主链与辅助关系视觉同权）：

```xml
<mxCell id="edge-aux" value="退回补齐" style="edgeStyle=orthogonalEdgeStyle;rounded=1;orthogonalLoop=1;jettySize=auto;html=1;strokeWidth=1.25;fontSize=12;strokeColor=#94A3B8;fontColor=#475569;endArrow=blockThin;endFill=1;dashed=1;dashPattern=6 4;"
  edge="1" parent="1" source="node-2" target="node-1">
  <mxGeometry relative="1" as="geometry"/>
</mxCell>
```

当用户明确要求动画或运动提示时，可以在部分关键边上使用 draw.io 的动画连接线样式：

```xml
<mxCell id="edge-2" value="事件流" style="edgeStyle=orthogonalEdgeStyle;rounded=1;orthogonalLoop=1;jettySize=auto;html=1;strokeWidth=2;strokeColor=#2563EB;fontColor=#1E3A8A;endArrow=blockThin;endFill=1;dashed=1;dashPattern=8 8;flowAnimation=1;flowAnimationDirection=normal;flowAnimationTimingFunction=linear;flowAnimationDuration=500;"
  edge="1" parent="1" source="node-2" target="node-3">
  <mxGeometry relative="1" as="geometry"/>
</mxCell>
```

动画连接线只优先用于 1 到 3 条关键流，而不是图表中的每条边。

### 示例驱动的补充图型规则

- 学术对比 / 量化矩阵图：并排 panel 优先顶部主体、底部 caption；矩阵或方格阵列保持严格对齐，强调靠少量高亮格、乘号或 α 等短符号，而不是给每个格子单独加长标签。
- 分层存储 / 算子流图：triangle、trapezoid、虚线 stage box、矩阵块和短统计标签都可以是主语义，不必强行改回圆角矩形；带宽、容量、loop 等说明应贴近对应对象。
- 分解 / agent-tool 路由图：主节点可以搭配独立的小型 icon text node 作为辅助图标；图标只补语义，不替代标题，类别色应按“分解 / LLM / 工具”这类稳定语义分组。
- 时序图：参与者放在顶栏，lifeline 用垂直虚线，消息用近似水平的直线箭头，时间严格自上而下；返回消息与调用消息分开布置，不要把时序步骤改画成普通流程框。

### 命名和布局约定

- 使用稳定前缀，让 XML 保持可读：
  - 节点：`node-1`、`node-2`、...
  - 边：`edge-1`、`edge-2`、...
  - 文本标签：`label-1`、`label-2`、...
  - 组/容器：`group-1`、`group-2`、...
- 尽可能匹配用户的语言。
- 优先使用简洁标签。
- 仅更改标签或边时，保留现有坐标。
- 记住 draw.io 坐标从左上角开始：x 向右增加，y 向下增加。
- 对新布局使用简单粗略网格，不要过度纠结坐标：列间距约 180 px，行间距约 120 px，只有在标签会重叠时再调整。
- 中文节点标签即使很短也要保留可读宽度：4 个汉字的流程节点宽度至少 80 px，5 到 6 个汉字通常至少 96 px。不要生成宽度 60 px 的常规流程节点，除非它是图标、编号或明确的极小标记。
- 对容器，将子元素的 `parent` 设为容器 ID，并使用相对于该容器的坐标。对不可连接的视觉容器添加 `pointerEvents=0`，让连接目标指向子单元，而不是容器外壳。
- 对泳道，`startSize` 标题带下方要留出清晰内容区：节点默认放在距泳道顶部 48 到 72 px 的稳定内容带内，而不是贴着标题带下缘排成一条线；若泳道较高而节点很少，优先把节点放进泳道的中部阅读带，避免看起来所有节点都挤在最上方。
- 对常见 `height=130~150`、`startSize=30` 的横向泳道，48 到 56 px 高的节点通常应放在 `y=58~68` 的阅读带，而不是全部卡在 `y≈48~52`；这样能把标题带、节点行和跨泳道走线分开，减少“所有节点都贴在泳道顶边”的观感。
- 输出前检查同一父级下所有可见顶点的矩形框：若两个节点的 x/y/width/height 区间重叠，先移动分支或扩展画布再交付；同一水平行的节点至少保留 16 px 间距，学术/紧凑图也不能用重叠换取紧凑。
- 普通流程图的主阅读路径保持单调：优先从左到右或自上而下推进，不要让主链路在下一行反向折返。循环、退回和修改用带标签的反馈边表达，终审、录用、拒稿等后续主节点应放在前一主节点的右侧或下方，而不是回到画布左侧。
- 主路径边默认服务于阅读，而不是仅服务于连接成功：箭头头部必须清楚落在目标节点外缘，端点不埋进节点正文；若默认正交边会穿过文本或让方向感变弱，优先调整节点位置、增加组间距、为边标签腾挪空白，必要时再用少量中继点，而不是接受“结构对但要靠猜”的成图。
- 放节点时先给边留版位：主链、长回路和跨区边默认拥有 20 到 40 px 的空白走廊；不要把节点、标题条和说明文字先贴满，再指望自动正交边从缝里钻过去。
- 长反馈边、跨分区回传和需要绕开标题带的边，优先使用“三段式折线”：先离开源节点，再沿空白走廊转向，最后进入目标节点。默认只写最少数量的中继点，目标是稳定可读，不是像素级雕刻。
- 边标签要与线条解耦：关系标签优先放在线段外侧或转折处附近，并用足够留白或 `labelBackgroundColor` 保证可读；不要让 `prepend`、`Top-k docs`、`修改后复审` 这类关键标签直接压在线上或压进邻近节点文字区。
- 对层级图、组织架构图或树形图，先从用户文本中逐项提取显式列出的实体和父子关系；只画这些实体。不要为了满足估算数量、示例数量、标题暗示或自认为缺失的部门而新增未列出的节点。若文本中的总数与枚举项冲突，枚举项优先；如果最终输出必须是纯 XML，就按枚举项画图，不在 XML 中补虚构节点。
- 树形图默认自上而下：父层 y 坐标更小，同级节点使用完全相同的 y 坐标；在生成坐标后核对最右节点的 `x + width`，让 `pageWidth` 至少覆盖该值并留出 24 px 以上边距，或先压缩横向间距后再设置页面宽度，避免节点被裁切。第三层/叶子节点使用明确浅色填充，例如 `#DBEAFE`、`#ECFEFF`、`#DCFCE7`、`#FEF3C7`，不要把所有叶子都设成接近白色的 `#F8FAFC`。
- 对分类树和组织树，兄弟分支的横向位置按整棵子树包络宽度决定，而不是只按父节点盒子宽度决定：先估算每个父节点下所有叶节点的总宽度与间距，再给相邻父分支之间预留 24 到 36 px 以上的分支间隔；如果两棵子树将发生交叉或右侧溢出，优先整体平移分支并扩展 `pageWidth`，不要只微调单个叶节点。
- 分类树完成坐标后，再做一次“同一 y 行叶节点”的全局扫描：按 x 从左到右排序，强制每个后继叶节点满足 `next.x >= current.x + current.width + 24`。若不满足，优先右移后继节点及其所属整棵分支，并同步更新 `pageWidth`，不要依赖肉眼估计“看起来差不多”。
- 树形图中的边先服务于标签可读性，再服务于最短路径：根节点到二层节点、二层节点到叶节点时，先从父节点底边短垂直离开 16 到 24 px，再在空白分叉带里水平展开；不要让正交边直接穿过二层标签中心或节点正文。
- 当根节点较宽、二层节点也是宽标签或双语标签时，不要把根到二层的边完全交给自动正交路由；默认在这些边的 `mxGeometry` 中写 1 到 2 个 points，让主干先落到根节点下方的公共分叉带，再分别转向二层节点上缘。只要位图里出现“根到左右分支的线压过二层标题”，就视为树形布线未完成。
- 学术图的“浅色”不等于多色：同一图中主体节点尽量使用 2 到 3 个浅底色，描边优先用 `#64748B`、`#94A3B8`、`#CBD5E1` 这类中性灰蓝；只有风险、拒绝或最终结论等少数节点使用更强强调色，避免一排节点各自使用高饱和描边。
- 画布紧凑度通过重平衡实现，而不是靠局部压缩实现：如果出现“大块空白”和“局部拥堵”并存，优先收紧无效留白、重新分配主链与支链节奏、扩展真正拥堵的簇；不要一边保留半页空白，一边让中央区域线条、标签和节点挤在一起。
- 长标签默认先保证完整可见，再追求紧凑：中英混排、副标题、论文术语和任务头若超过单行稳态长度，优先增宽节点、增加高度或拆成主标签 + 辅助说明；避免依赖脆弱的 HTML 片段、过小字号或裁切式换行。
- 只允许几何最小修补时，也要保护连线阅读带：如果长标签节点扩宽后仍与主链中心线冲突，优先增加受影响节点高度到稳定多行状态，并只对这些长标签节点做 8 到 16 px 的轻微上下错位或右移下游节点，让自动路由尽量走在节点之间的空白带，而不是穿过包裹后的文字区。
- 增量编辑、批量换色和最小修补也要过位图可读性：如果允许修改几何、页宽、标签位置或前景/背景对比度，就应把这些预算用于修复箭头、截断文本和低对比度，而不是只满足“ID 没变、XML 仍有效”。
- 页面尺寸贴合但不要贴边：把最底部或最右侧可见元素与 `pageHeight` / `pageWidth` 至少留出 24 到 36 px。若为了紧凑把画布收得很小，先确认脚注、标签和箭头没有贴近页面边界。
- 对返修评审流、显式枚举的组织树/分类树、机器学习方法图、RAG 架构、横向泳道图、三分支思维导图，以及学术对比矩阵图、分层存储示意图、代理/工具分解图和时序图等高频场景，优先套用 `references/visual-patterns.md` 与示例资产里已经稳定的范式，而不是继续向主技能内联更多特例。

### 默认视觉方向

- 优先使用白色页面、克制配色，以及仅 1 到 2 个强调色。
- 只有当容器能澄清模块、阶段或边界时才使用容器。
- 对明显的领域对象（决策、数据库、文档、参与者、云/提供商图标）优先使用语义正确的 draw.io 形状，同时保持整体视觉系统一致。
- 避免巨大的整页灰色块、彩虹配色、粗黑边框，以及混杂无关形状。
- 除非用户明确要求全局系统框，否则不要用一个过大的边界包住整页。
- 学术或文档场景遵循 `references/style.md` 中的规范。
- 汇报型流程图、产品架构图和学术方法图的实战视觉组织模式见 `references/visual-patterns.md`。

### 视觉增强策略

当用户要求“更好看”“更精致”“更适合汇报/幻灯片/论文展示”时，优先做能提升信息传达的视觉增强，而不是装饰性美化：

- **先建立视觉锚点**：每张图至少有一个一眼可见的主锚点，例如主标题区、核心方法块、关键决策节点或结果收束节点；不要让所有节点同色同权、看起来像一排无差别方框。
- **建立三级层级**：标题/分区标题是一级，主流程或主结构节点是二级，注释、边标签、证据层和辅助说明是三级。三级之间通过字号、字重、留白、描边强弱和底色轻重区分，而不是只靠更多颜色。
- **强调主路径，弱化辅助路径**：主路径边可略粗或使用更稳的颜色；反馈边、旁支边、证据边可用较浅色或虚线。这样读者先读懂主链，再回看补充关系。
- **避免均质节点汤**：当节点较多时，把同类节点做成成组的簇、分区标题条、轻量背景框或两行结构，避免整张图退化成大量相同圆角矩形平均铺开。
- **用浅色块而不是重边框分组**：分区优先靠浅底色、标题条和一致边距建立，不靠大面积深色块、粗黑框或整页包围框制造“设计感”。
- **控制色彩预算**：主体通常使用 2 到 3 种浅色底 + 1 个强调色即可。强调色只给关键节点、关键箭头或结论区，不要每个模块都争抢注意力。
- **层级先靠结构建立**：先用位置、大小、语义形状、背景分区和描边轻重建立主次，再决定是否需要额外颜色；不要把一组同质矩形仅靠换色硬拽出层级，也不要让所有模块都成为一级强调。
- **把空间节奏做出来**：紧凑不等于贴边或挤压。组内紧、组间松；主链紧、支链略松；标题和内容之间保留明确呼吸区，避免所有元素以同一间距机械排布。
- **把布线当成版式的一部分**：主链箭头、反馈边和跨组连接必须从空白区经过，而不是穿过正文中心；当边和字冲突时，优先重排空间或弱化辅助边，而不是接受线压字的结果。
- **让文本看起来像被设计过**：重要节点可采用主标题 + 副说明的两层文本；长说明移到旁注或分区说明，不把整段话塞进主流程节点。
- **有语义时再用图标/图片**：外部系统、数据库、输入输出介质、人物角色或论文组件可以用语义图标或形状强化识别。若使用 emoji 或 text icon，优先做成贴近主节点的独立小节点，而不是把图标塞进正文；数量要少，风格要统一，不能把图标变成装饰噪声。
- **按场景调视觉强度**：学术图优先克制和证据链；汇报或产品架构图可以更强调焦点、标题条和阶段分区；但两者都应避免高饱和渐变、厚阴影和营销海报式噱头。

### 渲染与预览策略

在交付 XML 之外，应尽量让用户看到最新图表源生成的 PNG 或等价截图，而不是只看到 XML 文本：

1. **结构校验优先**：使用 `scripts/mxgraph_validation.py` 对当前图表源做结构校验。
2. **导出级预览**：直接从 drawio 源生成 PNG 展示给用户；若宿主不支持直接导出 PNG，则说明无法提供可视预览。
3. **用户可见结果优先**：如果宿主支持附件、内嵌图片、预览面板或可点击导出链接，最终回答默认展示这些可视结果，并只用一句简短说明提示“可编辑源已更新”；不要在同一条最终回答里再粘贴整段 XML。
4. **导出预览的边界**：导出预览反映结构与几何，但不复刻 draw.io 的边路由、周界裁剪或标签避让；交付时说明这是导出预览，且建议在 draw.io 中打开以获得最终成图。
5. **无预览环境时如实降级**：如果以上路径都不可用，只交付裸 XML，并明确说明未完成视觉自检。

### 标准执行工作流

1. 定位宿主定义的图表源工件。
2. 如果它不存在，创建基础模板。
3. 判断用户想要新图表，还是修改当前图表。对修改请求，使用上面的增量编辑策略。
4. 检查现有 `mxCell` 块，并识别涉及的精确节点或边。
5. 规划最小的有效 XML 变更。
6. 可行时通过宿主的定向编辑能力应用；只有当宿主缺少修补能力，或改动确实覆盖工件大部分内容时，才使用完整写入。
7. 如果宿主存储完整 `.drawio` 包装，编辑选中的 `<mxGraphModel>`，并保留包装元数据，除非任务需要页面级更改。
8. 默认使用 `scripts/mxgraph_validation.py` 做结构校验；如果脚本不可用，才退化为人工结构检查：
   - 根结构仍然存在
   - ID 唯一
   - 每个可见顶点/边都有几何
   - 每条边都指向真实节点
   - 已删除节点没有留下悬空边
   - 标签和样式属性已进行 XML 转义
9. 如有可用导出器，就直接从 drawio 源产出 PNG 展示给用户；最终回答优先给这个可视结果，并只简短说明这是导出预览、建议在 draw.io 中打开以查看最终成图。
10. 按 `references/visual-review.md` 中的审查准则（rubric）审查截图；完成图片后至少检查：文字与对应图形或图片区块的位置关系是否清楚、箭头和连线是否合理、是否存在重叠或遮挡影响阅读，以及布局是否在不影响阅读的前提下尽可能紧凑。箭头和连线问题优先于视觉润色。
11. 如果发现文字与图形归属不清、箭头方向不清、端点错误、箭头头部被遮挡、连线交叉过多、标签压住连线、节点重叠、布局过松或过挤、或语义遗漏，返回第 4 步做最小修补，然后重新渲染、重新审查。
12. 默认最多迭代 3 轮；如果仍有严重箭头/连线错误且每轮都有明确改善，可以扩展到 5 轮。若无可用预览路径，交付时明确说明“未完成视觉自检”，并列出只完成了哪些结构校验。
13. 对增量编辑、批量换色和最小修补任务，也按同一位图标准审查：结构保持正确只是起点，不是免检理由。若截图里仍有箭头消失、长标签截断、低对比度或容器漂移，就继续做最小闭包修补。

### 渲染自检停止条件

只有同时满足以下条件，才能把图表执行视为完成：

- XML 结构校验通过，且没有悬空边、缺失几何或非法标签转义。
- 每条业务上需要的关系都由可见连接线表达，箭头方向与逻辑阅读顺序一致。
- 箭头端点连接到正确节点，箭头头部可见，不被节点、容器、标签或其他边遮挡。
- 文字、标签与其对应图形、节点、箭头或图片区块的归属清楚，不会因为位置错位让读者误判含义。
- 连接线没有造成主要阅读路径混乱；必要的反馈、分支或跨泳道连接能被一眼区分。
- 节点、边标签和容器标签没有明显重叠、截断、遮挡或跑出画布。
- 布局已经收紧到没有明显无效留白，但没有通过压窄节点、贴边或制造重叠来换取紧凑。
- 图表覆盖用户要求的关键元素，且没有因修补连线而删除或改写无关内容。

如果上述任一项不满足，应继续修补迭代；如果已达到迭代上限仍不满足，停止并报告剩余风险，而不是假装完成。

### 配方

配方 1：添加节点

- 找到下一个可用节点 ID。
- 选择靠近相关节点的位置。
- 插入新的顶点单元。
- 如果是在两个固定位置的现有节点之间插入，先计算中间可用空隙；在不移动原节点的前提下，让新节点尽量保持 80 到 96 px 以上宽度并居中放置。不要为了“保持布局”把中文标签压到 60 px 这类明显过窄的宽度；如果间隙不足，优先使用略小间距或轻微增加页面宽度，而不是改动原节点坐标。
- 示例：两个 120 px 宽节点分别位于 `x=40` 和 `x=260` 时，中间空隙为 100 px；插入 4 个汉字的新节点应使用约 `x=170, width=80`，而不是 `x=180, width=60`。

配方 2：添加连接

- 根据标签或先前上下文解析源节点和目标节点。
- 找到下一个可用边 ID。
- 插入一个带有 `source` 和 `target` 的边单元。

配方 3：重命名节点

- 找到 `value` 与旧标签匹配的节点。
- 除非用户要求更多改动，否则只更改 `value`。

配方 4：删除并清理

- 移除目标顶点单元。
- 移除所有 `source` 或 `target` 为该节点 ID 的边。
- 只有在用户明确要求时，才重新连接相邻节点。

### 健壮性规则

- 如果 XML 格式错误，恢复为有效文档，而不是写入半损坏的工件。
- 如果源以压缩 `.drawio` 图表内容形式到达，在推理或编辑前先解码。不要手工编辑压缩/base64 文本。
- 如果多个节点有相似标签，使用周围结构或位置选择最佳匹配。
- 如果布局含糊，优先保证节点和连接正确，而不是追求完美外观。
- 如果请求纯粹是样式调整，保留 ID 和连接关系；只更改样式，并在必要时为了可读性更改几何。
- 如果校验失败，先修复结构问题，再回头做视觉润色。一个有效、略朴素的图表胜过一个漂亮但损坏的图表。

### 最后提醒

你的工作不是把 XML 倒进聊天窗口。你的工作是将有效、纯文本的 draw.io / mxGraph XML 编辑持久化到宿主定义的图表源工件中，并尽可能让用户直接看到更新后的图表预览；只有用户明确索要源 XML，或环境被迫降级为纯文本时，才直接显示 XML 本体。
