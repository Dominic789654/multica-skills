# 实战视觉模式

用于需要“更好看”“更像汇报图”“更像产品架构图”或“更有论文图感”的 draw.io / mxGraph 图表。本文不重复定义 XML 契约，只补充三类高频场景下可直接复用的视觉组织模式。

## 使用原则

- 先决定主阅读路径，再决定颜色和分组；不要反过来先挑配色。
- 视觉增强优先通过层级、节奏和锚点完成，而不是通过更多装饰完成。
- 先为主路径和关键回路预留空白走廊，再放置辅助说明；不要等节点摆满后再让边被迫穿过文字区。
- 当模式与用户的显式结构冲突时，保留用户结构，只借用模式的视觉手法。

## 模式一：汇报型主路径图

适用场景：周报、组会、产品评审、方案汇报、PPT 单页说明。

- 版式：使用单条主路径或两段式主路径，阅读方向保持单调，通常从左到右。
- 锚点：把“核心结果”“关键节点”或“最终输出”做成一眼可见的收束点，不要让起点和终点同权。
- 结构：主路径节点 4 到 7 个最稳，辅助说明作为旁注、次级支路或浅色证据条，不要把所有信息都做成主节点。
- 视觉：主路径节点可略大、略深或使用更稳定的描边；辅助节点用更轻底色、更细线或更小字号。
- 留白：主路径节点之间的间距应稳定，组与组之间比组内略大，形成节奏而不是平均分布。

常见失误：所有节点同宽同色、终点不突出、说明文字直接塞进主路径节点、为了“简洁”把所有辅助信息删到只剩流水账。

## 模式二：产品架构分层图

适用场景：系统架构、平台能力图、服务拓扑、企业内部技术说明。

- 版式：优先使用分层或分区，而不是杂乱网状图。常见安全结构是“入口层 / 业务层 / 数据与基础设施层”或“用户面 / 控制面 / 数据面”。
- 锚点：让核心平台、核心服务或核心数据枢纽成为视觉中心，其余模块围绕它组织，而不是平均铺满画布。
- 结构：同层节点尽量等高对齐；跨层关系用有限数量的正交边表达，避免所有模块彼此互连。
- 视觉：层级靠浅色背景区、分区标题条和一致边距建立；核心模块可比外围模块多一个强调色或略粗描边。
- 语义：数据库、外部系统、用户入口、异步队列等优先用语义形状区分，但图标和特殊形状要少而准。

常见失误：每个模块都单独上色、背景框比内容更重、边交叉成网、没有主中心、把“组件清单”误画成“架构图”。

## 模式三：学术方法证据链图

适用场景：论文方法图、实验设计图、研究流程图、白皮书方法章节。

- 版式：优先采用“主方法链 + 证据支路”或“上方法下结果”的双层结构，不要把方法、实验、指标、结论全压成一条线。
- 锚点：核心方法模块或模型结构是第一锚点，评估指标和结论是第二锚点，读者应先看懂方法，再理解证据如何支撑结论。
- 结构：主链保持单调推进；消融、对照、指标汇总等支路围绕主链展开，并在结论处收束。
- 视觉：主体节点颜色克制，证据层更轻，结论节点可用唯一强调色或更清晰的边框突出，但不应变成海报式高饱和焦点。
- 文本：核心术语保留英文或标准缩写，解释性长句放在旁注或分区标题，不要挤进每个主节点。

常见失误：把学术图退化成 6 个同质矩形串联、结论节点和中间步骤同权、所有模块使用不同颜色、证据链方向反复折返。

## 通用布线补丁

用于任何模式下的高频视觉修补，尤其是 benchmark 里最容易丢分的箭头、压线和容器漂移问题。

- 主路径边优先走空白区，不穿过节点正文；如果默认正交边会压字，先调节点间距、组间距或节点宽度，再考虑少量中继点。
- 长反馈边、跨分区回传或穿越大标题带的关系，默认使用“走廊 + 三段式折线”：源节点外预留 20 到 40 px 脱离段，在空白带内转向，再进入目标节点；必要时在 `mxGeometry` 中写 1 到 2 个 `points`，不要把这类边完全交给自动正交路由。
- 箭头头部必须在目标节点边缘外清楚可见；不要让线段在位图里像“碰到了节点”却看不出指向。
- 边标签默认放在线段外侧或拐点附近；若关系重要但位置拥挤，给标签单独留白或使用浅色标签底，而不是把字直接压在线上。
- 当一张图同时存在长回路和短主链时，先保证主链最顺、回路次顺；不要为了闭环漂亮牺牲首次阅读路径。
- 如果图里开始出现“大块空白 + 中部拥堵”，说明不是空间不够，而是空间分配错了；优先重排簇与簇之间的节奏。

## 选择建议

- 用户强调“汇报、汇总、讲清楚流程”时，先试模式一。
- 用户强调“系统组成、平台关系、服务边界”时，先试模式二。
- 用户强调“方法、实验、指标、论文图”时，先试模式三。
- 如果一个请求同时落在两类之间，优先选语义更强的模式，再借另一类模式的视觉节奏。例如学术系统图通常以模式三为主，再借模式二的分层组织。

## 高频结构配方

这些配方用于承接不适合长期内联在主技能里的场景细则。遇到匹配场景时，优先复用这里的 recipe，不要继续把特例塞回 `SKILL.md`。

### 决策分支与返修流程

适用场景：论文评审、审批、审核、退回补齐、返修闭环。

- 含决策菱形的流程图中，每个分支结果使用独立行、列或泳道；“退回/补齐/拒绝”等旁支不要与主流程下一步放在同一坐标带内。
- 返修型流程默认保留闭环：作者修改后回到复审、外审或终审中的一个明确节点，并用边标签标明条件，不要把“修改”直接串到录用或终审结果。
- 若需要两行紧凑布局，主阅读路径仍保持单调；循环边作为反馈边处理，不让主链在下一行反向折返。

### 显式枚举的组织树与分类树

适用场景：组织架构图、方法论树、系统文献综述分类树。

- 先逐项提取用户显式列出的实体和父子关系，只画枚举出的节点；总数与常识冲突时，枚举项优先。
- 组织架构图逐项核对父子清单，例如 “CFO 下属有财务团队、审计团队” 就只生成这两个 CFO 子节点，不倒推补齐其他部门。
- 分类树先按每个主分支的叶节点数估算簇宽；簇内叶节点保留 16 到 24 px 间距，簇间保留 24 到 36 px 间距，相邻簇将重叠时优先扩展 `pageWidth` 或整体平移分支。
- 主分支之间按“子树包络”而不是“父节点宽度”排布。
- 每个二层主分支的横向占位，至少等于其所有叶节点总宽度加内部间距；相邻主分支的包络一旦相交，必须整体挪动整棵分支，而不是只移动单个叶节点补洞。
- 完成树坐标后，逐分支核对子树左右边界：左侧分支的最右叶节点必须满足 `rightLeaf.x + rightLeaf.width + 24 <= nextBranch.leftmostLeaf.x`；若不满足，先扩展画布或整体平移右侧分支，再考虑压缩局部间距。
- 完成所有叶节点坐标后，再做一次全局行内检查：把同一 y 坐标带内的叶节点按 x 排序，并逐对验证 `next.x >= current.x + current.width + 24`。taxonomy 图里只要这一条不成立，就视为布局未完成，即使视觉上似乎还能辨认。
- 主分支标题、双语副标题和方法名优先用纯文本换行或主标签 + 辅助说明处理；避免依赖复杂 HTML 片段把副标题硬塞进同一个框里，否则渲染时容易外溢压线。
- 根节点到二层节点、二层节点到叶节点都先走短垂直段再分叉：让边在节点之间的空白分叉带里展开，而不是直接穿过二层标签中心或让箭头头部埋进文字区。
- taxonomy 图里只要根节点和二层节点都比较宽，就默认给根到二层的三条主边写 `mxGeometry` 中继点；不要指望 `orthogonalEdgeStyle` 自动帮你避开二层标题。
- 系统文献综述常见的 3/3/2 结构可采用三组横向簇，叶节点围绕父节点居中；任意相邻叶节点满足 `next.x >= current.x + current.width + 24`。

### 学术方法证据链细化

适用场景：机器学习论文方法图、实验设计图、评估链路图。

- 当概念数超过 6 个时，优先使用两行证据链、分区网格或轻量容器，不把所有节点压成一条长横排。
- “结论”“论文结论”“适用边界”等收束节点通常承载最长语义，宽度不低于 140 px；关键指标节点通常不低于 150 px。
- 主证据链按用户列出的语义顺序排布；如果顺序是“消融实验 → 评估指标 → 结论”，结论应在评估指标右侧或下方的后续阅读位置。
- 机器学习方法图常用主链是“输入数据 → 特征编码 → 模型训练 → 消融实验 → 评估指标 → 结论”；紧凑布局放不下时优先扩展画布或改为三列两行，而不是压窄关键节点。
- 模型训练后的验证层默认分成两条支路：一条进入“消融实验 / 模块贡献”，另一条进入“评估指标 / 指标汇总”，再共同支撑“结论 / 适用边界”。
- 输出前按最终坐标重算页面边界：`pageWidth >= maxRight + 24`，`pageHeight >= maxBottom + 24`。
- 学术新图默认不加入可见的“本图说明”“主路径说明”“紧凑证据链说明”等底部解释标签，除非用户明确要求注释或图例。

### RAG 双流汇合图

适用场景：RAG、检索增强生成、查询/文档双路架构。

- Query 流和 Document 流必须在 Generator 处汇合：Query → Query Encoder → Retriever，Document Store → Retriever，Retriever → Top-k Documents → Generator，同时 Query 或 Encoded Query 也应连接到 Generator，最后 Generator → Output。
- 不要只画检索链路而遗漏生成阶段的问题输入，否则会把双流架构退化成单路检索图。

### 横向泳道与跨泳道回传

适用场景：多角色流程、交付链路、订单履约、跨部门协作。

- 横向泳道使用独立 `swimlane;horizontal=1;startSize=30;` 容器；泳道内节点的 `parent` 指向所属泳道，坐标相对泳道。
- 当泳道内节点依赖手工相对坐标时，不再叠加 `childLayout=stackLayout`、`horizontalStack` 等自动重排属性；泳道标题和节点都要在预览图中稳定留在各自泳道内。
- 节点不要贴着泳道标题带排布：在 `startSize=30` 的常见泳道里，节点顶部通常放在 `y=48` 到 `y=72` 的内容带内；如果所有节点都压在标题带下缘，读者会误判它们属于同一泳道顶部而不是各自职能区。
- 跨泳道边默认保留在根层；当路径会斜穿多个泳道或遮挡节点时，在边的 `mxGeometry` 中加入 1 到 2 个中继点，让路线先水平再垂直或先垂直再水平。
- 对跨泳道主流程，优先使用显式交接走廊：先从源节点水平走到节点外 20 到 40 px 的空白区，再垂直到目标泳道，最后水平进入目标节点。
- 不要让自动正交边贴着泳道顶边一路滑行，否则箭头端点和职能切换关系会变得模糊。
- 三泳道主流程不要依赖全自动正交边完成跨泳道交接：对“用户 → 平台”“平台 → 仓储”“仓储 → 用户”这类主边，默认写出 2 个中继点，让边先离开源节点 20 到 40 px，再沿泳道间空白走廊垂直到目标泳道后进入目标节点。
- 最后一个跨泳道回传可使用右侧交接走廊：目标节点放在源节点右侧，中继点放在两个节点右边界之后 20 到 40 px，避免连线穿越中间泳道内容区。

### 长标签与双语节点

适用场景：中英混排流程图、论文方法图、长任务名、带副标题的学术节点。

- 默认先给长标签足够宽度和高度，再追求整体紧凑；优先保持完整语义可见，而不是把节点硬压成统一窄盒子。
- 当同一行出现两个以上长标签节点时，先放宽主链关键节点，再调整相邻短节点位置或画布宽度，避免只让最后两个节点被截断。
- 主标签和辅助说明若语气不同，优先拆成两层文本，而不是用一整段同权长句塞满节点。
- 对只允许改几何的最小修补，若长标签节点扩宽后仍与主链水平连线共享同一中心带，优先把受影响长标签节点加高到约 72 到 88 px，并对这些长标签节点做 8 到 16 px 的轻微错位或把后续节点整体右移；不要把所有节点继续锁死在同一中心线，任由连线压过包裹后的文本。
- 末端长标签节点完成扩宽后，再复核右边距：`pageWidth` 至少覆盖最右节点右边界再留 36 到 48 px，不要让最后一个双语长标签贴着画布边缘结束。

### 三分支思维导图

适用场景：中心主题 + 3 个主分支的脑图、概念结构图。

- 中心节点接近画布几何中心，主分支分布在不同象限或角度扇区；底部叶节点与 `pageHeight` 至少保留 40 px。
- 正好 3 个主分支时，不要退化成简单上下三角形或只占左上/右上/右下三象限；至少让一个主分支或其叶节点进入左下区域，避免整张图右下过重。
- 每个叶节点连接到所属主分支，而不是直接回连中心。
